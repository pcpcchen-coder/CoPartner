交棒鏈

四道閘

模型回來的每個動作都是不可信提議。防線不靠 prompt——螢幕上出現的任何指令都可能是別人放的，所以防線必須在模型之外。四道閘任何一道都能單獨擋下來。

01出境閘門 EgressGate

逐欄位掃描信封並遮罩；PIPL 命中就整包拒出，呼叫端只准走本地階，不 fallback 雲端。

02Gateway 預算熔斷

LiteLLM 設 max_budget；路由不變式由 pytest 解析 config 斷言，不靠人記得。

03風險分級 + 人工確認

與模型推理無關的本地規則判 low／medium／high；high 在任何政策下都必須人按。危險指令保守偏殺——誤殺只是多按一次。

04沙箱執行

XPC service（雙向 code-signing 驗證）→ sandbox-exec sbpl → posix_spawn argv 直呼。全程沒有一個 shell。

兩次「第一次」

8 / 20 第一次真的執行命令（cat 讀回檔案，stdout 帶回對得上的 UUID）；9 / 3 第一次真的動使用者的電腦（HUD 確認後畫面捲動）。兩次翻開能力的那一行都單獨成立一個 PR——理由很簡單：翻開執行能力若混在一大包程式碼裡，沒有人（包括作者）能真的審完。翻回 false 是出事時的第一個動作，只需改一行。

允許

  • 只有 shell 一種動作
  • 只有固定表裡七個唯讀工具：cat ls head tail wc grep find
  • 只能寫沙箱工作目錄
  • 每個動作仍過本地風險分級 + HUD 人工確認
  • UI 動作（點按／輸入／捲動）走主程序，沒有沙箱可圍——防線只有風險分級、confirm-each 與 undo

拒絕

  • 永遠不含 shell 本身
  • 網路全斷、家目錄關閉、秘密路徑另外 deny
  • 檔案動作明確拒絕；UI 執行端刻意不支援截圖（截圖該由擷取管線產生並經出境閘門，偷截一張等於靜默拿掉整個出境設計）
  • 模型解析不出的組合鍵一律 high——不知道它會做什麼，更該問人

第一次真執行刻意用本地合成提議，走完全相同的路徑（風險分級 → HUD → token → 全部閘門 → XPC → sbpl）。它不繞過任何閘門，只是把提議來源從雲端換成本地，讓第一次真執行發生在完全受控的情況下。

驗收判定是「stdout 裡有那串隨機標記」，不是 didExecute == true——沙箱擋掉讀取時 cat 照樣會結束、didExecute 照樣為真，stdout 卻是空的。

方法論

沒有 Mac，怎麼寫 macOS app

開發代理跑在 Linux 容器，沒有 Mac、沒有 GPU、沒有螢幕、沒有權限、沒有 Apple Intelligence。這六條原則是被逼出來的，但逼出來的結果是每個平台依賴都變成一個明確的注入點。

01
可注入後端

平台重活（Metal／SCK／vec0／FoundationModels／computer-use／XPC）全藏在 protocol 後，CI 用假後端驗邏輯。真後端標 🔒。

02
誠實佔位

沒接線的真後端一律 throw .notWired，絕不靜默假成功。假成功會讓「還沒接」這個訊號永遠消失。

03
安全不變式寫進型別

ApprovalToken 的 init 是 internal，繞過閘門的呼叫路徑在編譯層面不存在；而且它不過 XPC 線——跨程序的值可以偽造。

04
先讓 endpoint 無害，再讓它有能力

XPC service 先做成沒有執行能力的骨架，驗簽補上後才翻開開關。安全性靠「根本沒有那個能力」，而非靠檢查。

05
build 綠 ≠ 真的編到了

canImport 為 false 時整檔靜默略過、build 照樣綠。在 #if／#else 兩側各放一個 #warning，看到黃字才算數。

06
驗證方式比被驗的東西重要

沙箱只測「擋得住」會得到假通過——deny-default 下什麼都跑不起來。改成成對驗證：負向結果依賴正向基準，基準沒過就標「無效」而非「通過」。

真機 dogfood

CI 永遠測不到的那種 bug

每一個都是綠燈狀態下藏著的。第一個尤其可怕：邏輯正確、測試也過——錯在真機餵給它的資料。

FOCUS 狂刷M2 · 同源共四類

終端機每輸出一個字就被判定換視窗，同一秒噴十幾行。根因是焦點追蹤誤用 AX value（欄位內容）當視窗識別。後來又抓到同源的另外三類：會變的標題、「讀不到」、兩個不同來源的欄位當身分。四條回歸測試釘住。

OCR 截整螢幕M2

混入選單列和其他 app 的文字，吞吐等同沒優化。改依 AX 焦點框裁切 → 像素吞吐降到 18%。

Vision bbox 用左下原點M2

與螢幕座標慣例相反，沿用會讓摘要上下顛倒。型別強迫呼叫端明講慣例，不讓人猜。

稽核不誠實M5

被閘門擋下的動作原本留下零痕跡；執行未成功時原本記成已執行。改成 attempt／executed／notExecuted／blocked 四態。

給 /tmp/x 的規則對 /private/tmp/x 永遠不匹配，而 profile 看起來完全正常。先 realpath，並補上路徑跳脫。

step 53.7 · 七輪

一場推翻了自己三次的記憶體診斷

症狀：沒開觀察、只是讓 app 開著就會跳系統記憶體告警。這一句話就排除了原本兩個主要嫌疑——它們都只在觀察開始後才存在。

+151 MB/小時→+7 MB/小時

成因：AsyncStream<TileEvent> 沒指定 buffering policy（無上限），而它唯一的消費者是一個 @MainActor 計數器——每個事件都要跳一次 MainActor，產生端不會等它。同一條管線上游的 SCKFrameProducer 早就用了 .bufferingNewest(2)。改成 .bufferingNewest(64) 後，出現了修正前完全沒有的 8 分鐘完全持平區段。

診斷過程推翻的三個中途結論

  1. 「持續成長」——一次性暖機被整體斜率攤成了成長率。
  2. 「還是在成長」——階段落差被攤成了成長率；斜率不該跨越狀態邊界。
  3. 「ratchet 確認：停止後不回落」——量測時機造成的假象。停止後 1–5 分鐘記憶體根本還沒開始掉，真正的落定點在 30 分鐘。

每一次都是同一種錯誤：一個看起來像資料的猜測，比「不知道」更糟。

附帶設計：刻意不用定時器取樣。要量的正是閒置路徑，在上面裝一個定時醒來的東西，等於在被觀察的對象裡加一個新的觀察者。改成每次打開選單取一個樣，背景成本恰好是零。

誠實清單

已知的風險與缺陷

列出來不是為了免責，是因為知道哪裡不確定本身就是進度。前兩條特別值得看——它們是寫在設計文件裡、後來被真機推翻的假設。

XPC 買到的不是權限降級

原本假設 service 跑在低權 _ambient user——做不到。內嵌 XPC service 必然與主 app 同 uid（實測 euid 501）。買到的是程序隔離，真正的圍籬來自 sbpl。記為殘餘風險 R5。

L1 會編故事

終端機標題 CoPartner — -zsh — 100×34 被 3B 腦補成「與 CoPartner 進行視訊會議」——日誌裡沒有任何視訊訊號。指令已明寫禁止臆測，3B 壓不住。這是 L1 品質調校，與 M5 是兩條線。

真 vec0 磁碟量未驗

盲寫風險低（sqlite-vec C API 穩定），但要裝 sqlite-vec 並跑滿 8 小時才知道磁碟量。step 36 專門驗這件事。

擷取仍是固定 2fps、每幀 hash 全螢幕

DYNAMIC 狀態機已測但還沒真正拿來降頻。step 23.5 的優化已排——是刻意延後，不是遺漏。

同 app 內換視窗仍記 FOCUS

這條路徑只有 CI 測試蓋到，dogfood 沒驗到（那次全程沒在同 app 內換視窗）。下次開兩個終端機視窗切一下就能補驗。

單人開發、V2+V3 合計約一年

緩解方式是每一版都設計成「該版結束即有完整可用產品」，不是半成品接力——V1 停下來也是一台可用的操作時間機器。
